# Tables per tournament

Set `table_count` for each independently organized category. For 12 tables split
equally between three categories, configure each tournament with 4 tables.
The application does not reserve a shared pool of physical tables across events.

Before grouping, the organizer can edit/save the count. Empty means legacy
grouping (preferred size 5 in lower groups, 3 in upper groups). Existing tournaments
remain null; generated groups are never regenerated by this change.

With a count, choose the feasible group count closest to the number of tables:
lower groups retain 4–6 players, upper groups 3–4. Balance sizes to differ by at
most one. Lower groups retain their MP snake seeding. Examples: 24/4 → 6,6,6,6;
22/4 → 6,6,5,5; 12/4 → 4,4,4. Existing Liga fallback is preserved.
If there are more groups than tables, the lower-group generation asks for
confirmation; the organizer coordinates sequential use. This is group planning,
not automatic per-match table assignment or scheduling.

The new-form preview uses maximum attendance; generation uses actual registered
participants. Save edits before generating. A database trigger prevents changing
the count after any groups/matches exist. Positive integers or null are accepted.

Validation: TypeScript/build/targeted ESLint; group-planning.cjs exhaustive cases;
tables-ui.cjs covers create/edit/generate with 24 participants, four groups of six,
60 matches and all participants assigned once using isolated API fixtures.
